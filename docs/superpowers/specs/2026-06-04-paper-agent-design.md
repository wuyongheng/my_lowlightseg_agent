# 低光照语义分割论文阅读 Agent 设计文档

## 目标

做一个第一版命令行论文阅读 Agent，服务于低光照语义分割研究。

这个 Agent 接收两类输入：

- 论文 PDF
- Markdown 读书笔记

输出一份结构化 Markdown 笔记，固定包含这 6 个部分：

1. 论文研究问题
2. 方法整体框架
3. 创新点
4. 实验设置
5. 和我的研究方向的关系
6. 可以参考的改进点

第一版的要求不是“大而全”，而是“能稳定用、便于扩展”，为后续升级到实验日志分析 Agent、组会汇报生成 Agent、低光照语义分割科研助手打基础。

## 范围

### 第一版要做的

- 命令行使用方式
- 同时支持 PDF 和 Markdown 输入
- 优先把 PDF 路径做好
- 输出结构化 Markdown 笔记
- 默认走本地解析流程
- 预留可选的多模态增强流程
- 输出内容要和低光照夜间语义分割研究相关，而不是泛化成普通论文摘要工具

### 第一版先不做的

- Web 界面
- 多 Agent 协作
- 引文网络分析
- 完整论文库管理
- 自动生成汇报幻灯片
- 复杂的图表 OCR 流程
- 完整训练日志分析功能

## 用户与使用流程

目标用户是做“低光照增强服务于下游夜间语义分割”的研究生。

预期使用流程：

1. 把论文放进 `data/papers/`，或者直接给一个 Markdown 笔记路径。
2. 在命令行运行 Agent。
3. 在 `notes/` 目录下得到一份结构化阅读笔记。
4. 后续把这些笔记继续用于实验设计、组会汇报和研究思路整理。

## 设计原则

- 第一版坚持 CLI 优先，不先做界面。
- 先用本地可控的解析，再调用模型做总结。
- 多模态只在确实能提升效果时启用。
- 模块划分要服务于后续升级，不能写成一次性脚本。
- 输出内容要稳定、清晰，能直接作为科研笔记复用。
- 整体研究视角要始终围绕“下游夜间语义分割收益”，不能跑偏成纯低光照图像增强。

## 总体结构

项目目录建议如下：

```text
paper_agent/
|-- data/
|   `-- papers/
|-- docs/
|   `-- superpowers/
|       `-- specs/
|-- notes/
|-- tools/
|   |-- pdf_reader.py
|   |-- paper_summarizer.py
|   `-- experiment_analyzer.py
|-- agent.py
|-- prompts.py
`-- README.md
```

逻辑流程如下：

1. `agent.py` 作为命令行入口，解析参数并选择处理模式。
2. 输入判断模块识别当前文件是 PDF 还是 Markdown。
3. 如果是 PDF，交给 `tools/pdf_reader.py` 做解析。
4. 如果是 Markdown，直接进入总结流程。
5. `tools/paper_summarizer.py` 负责生成固定的 6 个输出部分。
6. `tools/experiment_analyzer.py` 负责抽取实验设置、数据集、指标、对比方法、消融信息。
7. 最终把结果写入 `notes/` 目录下的 Markdown 文件。

## 处理模式设计

第一版支持 3 种模式：

- `default`：本地解析 + 文本总结
- `multimodal`：强制启用多模态分析
- `auto`：先本地解析，必要时再切到多模态

### 推荐默认模式

对用户推荐 `auto`，但第一版实现时要先把本地解析主路径做扎实，多模态先作为可选增强，而不是强依赖。

## 输入处理设计

### PDF 路径

PDF 是第一版的重点。

`tools/pdf_reader.py` 需要完成这些事：

- 提取 PDF 原始文本
- 在有必要时保留页码边界
- 尝试识别常见论文章节结构
- 抽取基础元信息
- 输出一个“解析质量信号”

这个“解析质量信号”可以先用简单启发式规则实现，比如：

- 提取出的文本非常少
- 断行严重、格式破碎
- 出现明显乱码
- 常见论文章节缺失
- 很多关键信息只存在于图表里，文本里体现不出来

如果解析质量低，且当前模式是 `auto`，就切换到多模态分析。

### Markdown 路径

Markdown 输入处理可以保持简单：

- 直接读取文件内容
- 尽量保留已有标题结构
- 接入和 PDF 相同的总结管线

虽然第一版支持 Markdown，但实现优先级还是以 PDF 为主。

## 总结模块约定

`tools/paper_summarizer.py` 应该返回一个固定结构的数据对象，对应那 6 个输出部分。

它至少要完成这些任务：

- 识别论文的核心任务和问题设定
- 用较高层视角还原方法整体框架
- 抽取作者显式提出或隐含体现的创新点
- 识别数据集、指标、基线方法和消融实验
- 把论文内容和你的研究主线建立联系
- 给出尽量具体的改进建议，而不是泛泛而谈

其中第 5 和第 6 部分必须带着下面这个研究前提来写：

- 低光照增强在这里的意义，是为了提升下游夜间语义分割
- 不能让“纯图像增强讨论”主导最终输出

## 实验分析模块约定

`tools/experiment_analyzer.py` 主要负责结构化提取这些信息：

- 数据集
- 评价指标
- 对比基线
- 消融设置
- 作者报告的优势和短板

这个模块后续要能复用到：

- 实验日志分析
- 结果表分析
- 汇报材料生成

所以第一版虽然功能不重，但接口边界要提前留好。

## Prompt 设计

`prompts.py` 里建议放可复用的提示词模板，至少包括：

- 通用论文总结 Prompt
- 面向研究方向关联的 Prompt
- 面向改进点生成的 Prompt
- 可选的多模态分析 Prompt

Prompt 设计要保证：

- 输出简洁但具体
- 6 个部分尽量完整
- 当证据不足时不要强行编造
- 当论文表述不清时，要显式说明不确定性

## 输出格式

每次运行生成一份 Markdown 文件，写到 `notes/` 目录。

建议命名方式：

- `<论文文件名>_summary.md`

固定输出结构如下：

```markdown
# 论文标题

## 1. 论文研究问题
## 2. 方法整体框架
## 3. 创新点
## 4. 实验设置
## 5. 和我的研究方向的关系
## 6. 可以参考的改进点
```

附加章节以后可以再扩展，但不应该进入第一版的硬性范围。

## 命令行设计

第一版命令形态建议如下：

```bash
python agent.py --input data/papers/example.pdf --mode auto
python agent.py --input notes/example.md --mode default
```

第一版参数建议先保留这几个：

- `--input`：必填，输入文件路径
- `--mode`：可选，支持 `default`、`multimodal`、`auto`
- `--output`：可选，自定义输出路径
- `--topic`：可选，为以后扩展研究方向预留

不要一开始就加太多参数，否则第一版会很散。

## 错误处理

命令行在这些情况下要给出清晰报错：

- 输入文件不存在
- 文件类型不支持
- 提取后内容为空
- 用户要求多模态，但多模态依赖不可用

回退策略建议如下：

- `default` 模式下，如果解析质量差，只提示风险，不自动切换
- `auto` 模式下，如果解析质量差，且多模态可用，则自动尝试多模态
- 如果多模态不可用，则继续输出尽力而为的本地总结，同时注明可信度限制

## 测试策略

第一版至少要覆盖这些测试点：

- PDF 路由是否正确
- Markdown 路由是否正确
- 输出文件是否成功生成
- 6 个固定章节是否都存在
- 坏输入时是否能优雅失败
- `auto` 模式的切换规则是否生效

第一版不必把测试做得很重，轻量单测加一两个端到端样例就够了。

## 后续升级路径

这个设计是为了顺着你的规划自然往后长：

1. 论文阅读 Agent
2. 实验日志分析 Agent
3. 组会汇报生成 Agent
4. 低光照语义分割科研助手

后续可复用的关键点有：

- `notes/` 里的结构化阅读笔记
- `experiment_analyzer.py` 的实验信息抽取能力
- `prompts.py` 里的提示词模板
- `agent.py` 的统一入口

## 第一版实现边界

为了控制范围，第一版只实现这些内容：

- 基础目录搭建
- 命令行入口
- PDF 解析
- Markdown 解析
- 结构化总结
- Markdown 笔记输出

不要在第一版里直接把后面的实验日志、汇报生成、科研助手都一起做进去。

## 已经确定的关键决策

- 输入支持：PDF 和 Markdown 都支持，但优先把 PDF 做好
- 产品形态：命令行工具
- 架构策略：混合式，默认本地解析，必要时启用多模态增强

## 风险与应对

- 风险：PDF 解析质量波动很大
  - 应对：加入简单的解析质量判断，并提供 `auto` 模式

- 风险：输出退化成普通论文摘要，和你的研究方向关系不强
  - 应对：把研究方向约束直接写进 Prompt

- 风险：第一版越做越大，最后变成一个难以收口的平台项目
  - 应对：把第一版契约收紧为“一次输入，一份结构化笔记输出”

## 第一阶段交付目标

第一阶段的目标很明确：

做出一个能真正跑起来的 CLI 工具，输入一篇论文，输出一份可复用的、包含 6 个固定部分的结构化 Markdown 阅读笔记。
